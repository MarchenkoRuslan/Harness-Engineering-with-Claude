### System 4 — Orchestration

11. **Push work down.** Defects the SQL query returned vs warm-tier total. Name the indexed query. Why does the model never see the full history?
    → My [seed.log](system4/seed.log) records **40 rows in the warm tier and 17 returned** for `since=2026-04-01T00:00:00Z`; SQLite's plan uses `idx_defects_ts`. `WarmStore.defects_since()` in [shift_monitor/warm.py](Build%20a%20Multi-Shift%20Quality%20Monitoring%20System%20with%20Claude%20Orchestration/04-fork-scratchpad/solution/shift_monitor/warm.py) runs `SELECT * FROM defects WHERE ts > ? ORDER BY ts DESC LIMIT ?`. The pipeline constructs its prompt from hot state and only those 17 rows, not the 40-row history, so SQL performs temporal filtering before context construction. My [run_shift.log](system4/run_shift.log) reports `shift C: 17 new defects`; this run used a recorded response rather than a live model call.

12. **Crash recovery.** The resume-vs-fresh decision and its staleness threshold (`recovery.py`). Why is a fresh start with an injected summary sometimes more reliable than resuming?
    → `decide()` in [shift_monitor/recovery.py](Build%20a%20Multi-Shift%20Quality%20Monitoring%20System%20with%20Claude%20Orchestration/04-fork-scratchpad/solution/shift_monitor/recovery.py) resumes an incomplete manifest when its last step is **at most 30 minutes old**, including exactly 30 minutes; an empty or complete manifest, or an incomplete one older than 30 minutes, selects `fresh`. Starting a new session with captured findings injected as a summary is the intended stale-recovery strategy: retain durable findings without trusting an obsolete working context, although the current CLI does not integrate this decision into its normal shift pipeline. In [shift_monitor/fork.py](Build%20a%20Multi-Shift%20Quality%20Monitoring%20System%20with%20Claude%20Orchestration/04-fork-scratchpad/solution/shift_monitor/fork.py), `fork_for_hypothesis()` copies the base hot-state file into a directory named for each hypothesis; callers give each fork its own scratchpad path, so fork writes do not mutate the base state or another fork's scratchpad. `merge_findings()` appends fork entries to the main scratchpad only when explicitly called; context isolation is therefore maintained by separate file paths and deliberate merging, not automatic shared mutation. My [33-test log](system4/pytest.log) records the recovery truth table, `test_fork_for_hypothesis_copies_state_without_mutating_base`, `test_two_forks_produce_independent_scratchpads`, and `test_merge_findings_appends_without_rewriting_existing` as passing; these tests, not my [recorded-response shift](system4/run_shift.log), provide the recovery/fork evidence.

13. **Small state.** Byte size of your `hot_state.json`. Why does the budget matter for a system run once per shift, indefinitely?
    → My [state_metrics.txt](system4/state_metrics.txt) records a **965-byte hot-state file**, under the **5,120-byte budget** enforced by `HotState.write_atomic()` in [shift_monitor/state.py](Build%20a%20Multi-Shift%20Quality%20Monitoring%20System%20with%20Claude%20Orchestration/04-fork-scratchpad/solution/shift_monitor/state.py). A bounded hot tier prevents prompt size from growing with every shift and leaves the historical record in warm/cold storage. The offline shift produced one [scratchpad entry](system4/data/shift_scratchpad.jsonl) and the [17-defect summary](system4/run_shift.log); the final [hot_state.json](system4/data/hot_state.json) is included for independent size verification.

14. **Three layers.** Point to a file/artifact for each layer and justify.
    → **Model:** Claude Haiku 4.5 generates responses and tool requests through the API client constructed by `make_client()` in [claims_intake/client.py](Build%20a%20Claims%20Intake%20Agent%20with%20a%20stop_reason-Driven%20Loop/exercises/03-dynamic-decomposition/solution/claims_intake/client.py); the model's returned decisions are visible in my [claim 04 trace](system1/runs/20261027_151442/traces/claim_04_neighbor_injury.jsonl), rather than being implemented by Python. **Harness:** [claims_intake/loop.py](Build%20a%20Claims%20Intake%20Agent%20with%20a%20stop_reason-Driven%20Loop/exercises/03-dynamic-decomposition/solution/claims_intake/loop.py) owns the `messages.create()` call and `stop_reason` dispatch, while [tools.py](Build%20a%20Claims%20Intake%20Agent%20with%20a%20stop_reason-Driven%20Loop/exercises/03-dynamic-decomposition/solution/claims_intake/tools.py) validates and executes actions; the Claude Code [CLAUDE.md](system3/config/CLAUDE.md) configures another harness surface, checked by my [validator](system3/validator.log). **Orchestration:** `run_shift()` in [shift_monitor/pipeline.py](Build%20a%20Multi-Shift%20Quality%20Monitoring%20System%20with%20Claude%20Orchestration/04-fork-scratchpad/solution/shift_monitor/pipeline.py) assembles each shift's bounded state and SQL slice, invokes the client once, and persists the next state outside the conversation, as evidenced by my [shift log](system4/run_shift.log) and [state metrics](system4/state_metrics.txt). Recovery and fork modules supply additional cross-session decisions tested separately; they are not model reasoning or loop-level tool dispatch.

15. **Deterministic vs prompt.** Cite one behavior guaranteed in code (terminal tool, read-only allowlist, atomic write, byte budget) and one guided by prompt. When is each right?
    → Deterministic runtime enforcement in [claims_intake/tools.py](Build%20a%20Claims%20Intake%20Agent%20with%20a%20stop_reason-Driven%20Loop/exercises/03-dynamic-decomposition/solution/claims_intake/tools.py) rejects routing without classification/severity and rejects a second terminal action; my [test log](system1/pytest.log) verifies those guards. The AST checks in [tests/test_antipatterns.py](Build%20a%20Claims%20Intake%20Agent%20with%20a%20stop_reason-Driven%20Loop/exercises/03-dynamic-decomposition/solution/tests/test_antipatterns.py) deterministically reject prohibited source patterns during verification, but do not constrain the model at runtime. In contrast, the submitted [.claude/commands/review.md](system3/config/.claude/commands/review.md) asks Claude to clarify ambiguous intent and follow must-report/skip criteria: that is prompt-based review guidance, not a programmatic guarantee of good judgment, and my [S3 tests](system3/pytest.log) validate its configuration/content rather than a live review. Similarly, the S1 confidence instruction did not ensure terminal action: all six [escalations](system1/runs/20261027_151442/escalations.jsonl) came from the backstop. Use code and regression tests for invariant enforcement, and prompts for context-dependent judgment inside those boundaries.

16. **Context, two faces.** Compare context management in System 2 (intra-session) and System 4 (cross-session) with cited numbers from both. Same principle, different mechanism — how?
    → S2 reduced one conversation from 38,708 to 16,775 tokens (56.66%) by summarizing resolved issues while preserving the active issue ([budget.json](system2/runs/20261027-151722/budget.json)). S4 selected 17 of 40 defects for a shift and retained a 965-byte hot state under a 5,120-byte budget ([seed.log](system4/seed.log), [state_metrics.txt](system4/state_metrics.txt)). ### Verification

17. **Reliability you can't see in one run.** Name one behavior a test guarantees that a single successful run would not reveal. Why does it matter before shipping?
    → [tests/test_run_backstop.py](Build%20a%20Claims%20Intake%20Agent%20with%20a%20stop_reason-Driven%20Loop/exercises/03-dynamic-decomposition/solution/tests/test_run_backstop.py)::`test_claim_without_terminal_tool_is_escalated` scripts a fake response with `stop_reason="end_turn"` and no terminal tool, then asserts that the runner sets the outcome to `escalated` and writes the expected claim ID to the escalation file. The same log also records `test_loop_raises_on_unexpected_stop_reason`, covering a stop mode absent from the live traces, so both domain fallback and exceptional loop termination are checked before shipping.

    → In S1, a bad decision can put one claimant's record into the wrong queue or escalate it unnecessarily; my [summary](system1/runs/20261027_151442/summary.md) shows six escalations, all through the runner's fallback. `route_to_adjuster` validates classification and severity and terminal actions are single-use in [tools.py](Build%20a%20Claims%20Intake%20Agent%20with%20a%20stop_reason-Driven%20Loop/exercises/03-dynamic-decomposition/solution/claims_intake/tools.py), while [Budget](Build%20a%20Claims%20Intake%20Agent%20with%20a%20stop_reason-Driven%20Loop/exercises/03-dynamic-decomposition/solution/claims_intake/budget.py) checks input tokens and elapsed time before each call.
